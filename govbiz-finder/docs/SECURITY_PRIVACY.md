# 보안 및 개인정보 보호 명세

## 1. 핵심 위협
- 타인이 공개된 사업자번호로 기업 계정을 선점
- 사업자번호만 입력해 타 기업의 기존 프로필·이력 조회
- IDOR/권한검사 누락으로 기업 간 데이터 노출
- 계정 열거, 무차별 로그인, 세션 탈취
- SQL Injection, XSS, CSRF
- API 키 및 개인정보 로그 노출
- 공고문·첨부파일을 통한 악성 입력 및 프롬프트 인젝션

## 2. 인증과 기업 관계 확인
사업자등록번호는 공개될 수 있는 식별값이며 인증수단이 아니다.
- 사업자번호 + 비밀번호만으로 기존 기업 계정의 소유권을 주장하거나 기업 데이터에 접근하도록 허용하지 않는다.
- 가입 절차는 `계정 생성`과 `기업 관계 확인`을 논리적으로 분리한다.
- 최초 기업 관계 확인을 통과하기 전에는 기업 프로필·검색 이력·관심 공고·추천 이력에 접근할 수 없다.
- 초기에는 대표자 본인확인 후 사업자 정보와 대조하는 단일 인증 흐름을 우선 검토한다. 필요한 경우 사업자등록증 증빙 등 대체 흐름을 둘 수 있다.
- 휴대전화 본인확인만으로 해당 기업 소속이 확인됐다고 간주하지 않는다.
- 인증 제공자 도입 시 비용·개인정보 처리·연동 요건을 별도 확인한다.
- 계정 존재 여부가 드러나는 메시지를 피한다. 예: “해당 정보로 진행할 수 있는 계정이 있는지 확인이 필요합니다.”
- 계정 복구에도 기업 관계 재확인을 요구한다.
- 초기에는 기업당 대표 계정 1개로 제한하고, 직원 초대는 후속 기능으로 둔다.

## 3. 비회원/회원 권한
### 비회원
- 공개 공고 검색·상세·공식 원문 이동·공개 첨부파일 다운로드
- 기업별 저장 데이터 접근 불가
- 지속 검색 이력 저장 불가(브라우저 세션 내 임시 상태는 허용 가능)

### 회원(기업 관계 확인 완료)
- 본인에게 권한이 부여된 기업 프로필
- 기업별 추천 결과, 검색/열람 이력, 관심 공고
- 알림 설정
모든 요청에서 서버 측 권한을 재검증한다.

## 4. 필수 보안 통제
- 비밀번호 Argon2id 또는 적절한 bcrypt 해시
- 사업자번호 등 식별정보 암호화 및 마스킹
- 기업별 서버 측 접근통제와 IDOR 테스트
- HTTPS 및 보안 쿠키(HttpOnly, Secure, SameSite)
- CSRF 방어, XSS 출력 인코딩, SQL 파라미터 바인딩
- 로그인/API rate limit 및 실패 지연
- 세션 회전·만료·로그아웃 무효화
- 관리자 권한 분리 및 관리자 변경 로그
- 비밀키 서버 저장, 저장소 커밋 금지
- 개인정보 로그 마스킹
- 백업·복구 테스트
- 업로드 파일 검증(허용 형식·크기·MIME·파일명 정규화)
- 외부 데이터는 비신뢰 입력으로 처리

## 5. 암호화 및 사업자번호
- 사업자번호는 평문 저장을 피하고 애플리케이션 레벨 암호화 적용을 검토한다.
- 정확 일치 검색이 필요하면 별도 비밀키 기반 HMAC 인덱스를 사용하고, 암호문과 분리한다.
- 암호화 키는 코드/DB와 분리된 환경 비밀로 관리한다.
- 화면·로그·분석 이벤트에는 마스킹된 번호만 표시한다.

## 6. 개인정보 최소화
- 추천에 불필요한 개인정보는 수집하지 않는다.
- 각 항목별 수집 목적·필수 여부·보유기간·삭제 절차를 명시한다.
- 기업정보와 개인 사용자 계정정보를 분리한다.
- 사용자 열람·수정·삭제 요청 처리 기능을 설계한다.
- 실제 운영 전 개인정보 처리방침과 동의 문구를 서비스 기능에 맞춰 작성한다.

## 7. 보안 테스트
- 사용자 A가 사용자 B/기업 B의 데이터에 접근할 수 없는지
- company_id를 조작해도 서버가 차단하는지
- 인증 미완료 계정이 기업 데이터에 접근할 수 없는지
- 사업자번호만으로 계정 존재 여부·이력을 추측할 수 없는지
- 로그인 반복 실패 제한
- XSS/SQLi/CSRF 기본 테스트
- 비밀키가 프론트엔드 번들·로그에 없는지
